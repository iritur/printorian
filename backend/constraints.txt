# Pinned versions for a reproducible build.
#
# Every dependency in `pyproject.toml` is a floor (`>=`), which is the right way
# to declare what the code needs and the wrong way to build the same image twice:
# two builds of one commit could resolve different versions, and a bad upstream
# release reached the farm without anything changing in this repository.
#
# So `pyproject.toml` keeps saying what is *required* and this says what is
# *installed*. Applied by the Dockerfile, by CI, and by DEVELOPMENT.md's setup —
# a constraints file that only some of those honour pins nothing.
#
# Regenerate deliberately, never by hand:
#
#     pip install -e ".[dev]" --upgrade
#     pip list --format=freeze | grep -viE '^(printorian|pip|setuptools|wheel)==' | sort > constraints.txt
#
# then let CI prove the new set before it is merged — which is the whole point of
# having it, and what makes Dependabot's grouped pull requests meaningful.
#
# **Nothing here may be a version some other package pins exactly.** `pydantic`
# requires `pydantic-core==2.46.4` — the exact string, because the two ship as one
# library in two halves — so listing the core here pinned a number that was
# already decided, and handed Dependabot a package it could raise on its own.
# It did, to 2.48.0, and the result was a file no resolver can satisfy:
#
#     pydantic 2.13.4 depends on pydantic-core==2.46.4
#     The user requested (constraint) pydantic-core==2.48.0
#     ERROR: ResolutionImpossible
#
# There was no forward fix either: no pydantic 2.x consumes 2.48.0 yet. So the
# core is simply absent from this file. Nothing is lost — pinning `pydantic`
# determines it exactly — and the conflict cannot recur, which is why there is no
# `ignore` for it in `.github/dependabot.yml` either. Prefer this to an ignore
# whenever a pin is redundant: an ignore silences the symptom, removing the
# redundant pin removes the thing that could go wrong.
#
# **A constraint applies only if the package is installed at all**, so this file
# does not have to know about platforms: `uvloop` is pulled by `uvicorn[standard]`
# on Linux and not on Windows, and is simply absent here rather than wrong. The
# set below was resolved on Windows; anything Linux-only resolves freely until it
# is added, which is a gap this file narrows rather than closes.
